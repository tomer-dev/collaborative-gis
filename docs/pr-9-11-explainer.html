What PR #11 and PR #9 add

Two independent lanes of M1. #11 is the browser-side polygon tool and its maths. #9 is the PostGIS tables the polygons land in. The demos below run the same algorithms as the PR code, ported line for line to plain JavaScript.

PR #11 Draw library (apps/web/src/lib/geo/)

Three files, no drawing plugin. Leaflet 1.9.4 gives us a Handler base class (enable/disable, same as its own drag or scroll-zoom handlers); the PR builds the polygon tool on it so later milestones can swap the base layer without losing the sketch.

draw-handler.tsPolygonDraw extends L.Handler. Click adds a vertex, drag moves one, Enter / double-click / first-handle click closes, Backspace undoes, Esc cancels. Fires draw:vertex, draw:change, draw:done, draw:cancel, draw:invalid.
geodesic.tsArea of the ring on the WGS84 sphere (Chamberlain & Duquette). Powers the live km² readout before the server computes the authoritative ST_Area(geography). Within 0.07 % of PostGIS on the test polygons.
self-intersection.tsPlanar O(n²) segment check so a bow-tie never reaches POST /areas. Adjacent edges may touch at their shared vertex but must not fold back. Server ST_IsValid stays the authority.

What invalidReason() checks on finish, in order: the shared Zod PolygonSchema (closed ring, at least 4 positions, at most 1,000, lng/lat ranges), then hasSelfIntersection(). The vertex cap is enforced earlier, in addVertex.

Spherical area, the formula

A = R² / 2 · | Σ (λ[i+1] − λ[i−1]) · sin φ[i] |
R = 6 371 008.8 m  (GEO.EARTH_RADIUS_M)

One pass over the vertices, no projection. Works for either winding and for open or closed rings. It ignores rings that cross the antimeridian or contain a pole, which the Israel-centred map never produces.

Why a hand-rolled handler

Not because of the map projection: Leaflet-Draw and Geoman work on LatLngs through Leaflet's own projection and would survive a CRS swap too. The reasons are what the handler has to do for this app: keyboard operation (Enter, Esc, Backspace, a focusable container with a role and label), the shared Zod polygon rules and the self-intersection check run before draw:done, events shaped for the WebSocket draft protocol, and every size and string from the shared constants. Leaflet-Draw is unmaintained (last release 2018); Geoman is maintained but weak on a11y and brings its own toolbar and CSS.

Constants (vertex cap, handle sizes, aria label, reasons) live in packages/shared/src/constants.ts, not in the file.

PR #9 Database schema (apps/api/src/db/, apps/api/drizzle/)

Drizzle ORM schema plus the generated SQL migrations, a custom PostGIS column type, a migration runner, and a real-PostGIS test project in Vitest. Nothing here is reachable over HTTP yet; T2 (spatial helpers) and T15 (routes) build on it.

Three tables

TableRoleKey columns
areascurrent state of each polygon; soft deletegeom geometry(Polygon,4326), area_km2 numeric(14,6), version int default 1, deleted_at
area_versionsone row per saved version (history, revert)PK (area_id, version), copies of geom/name/area, changed_by
audit_logappend-only who-did-whatuser_id, action, entity, entity_id, ip, user_agent, payload_hash
Decision D20 (after this PR): payload_hash is dropped and a nullable version is added, so an area event points at its area_versions row instead of hashing the body. Lands as migration 0003 with the routes PR.

The spatial index is partial: CREATE INDEX areas_geom_gist ON areas USING gist (geom) WHERE deleted_at IS NULL. Viewport queries only ever read live rows, so deleted ones do not bloat the tree.

Why a custom column type

Drizzle 0.45's built-in geometry() only emits geometry(point) whatever you pass it. The PR adds polygon() via customType:

dataType:   geometry(Polygon,4326)
toDriver:   ST_GeomFromGeoJSON($json)
fromDriver: polygonFromEwkb(hex)

Writes hand GeoJSON to PostGIS as a bound parameter. Reads never touch the column raw: the spatial helpers select ST_AsGeoJSON(geom)::json, so Postgres returns GeoJSON and the Node side parses nothing. (The first draft of #9 carried a 40-line hex EWKB parser for the read path; it was dead code once the helpers existed and was removed in PR #15, where a raw read now throws a pointer to ST_AsGeoJSON.) The EWKB demo below shows what the driver hands back and why reading it in SQL is the simpler layer.

Migration flow

    

      
1. edit schema.tsDrizzle tables in TypeScript. Column names are spelled out in snake_case because no casing option is set.

      
2. drizzle-kit generateWrites drizzle/0001_areas.sql plus a JSON snapshot. 0000_postgis.sql is hand-written: CREATE EXTENSION postgis.

      
3. migrate.tsRuns the journal in timestamp order over a per-request pg.Client. CI and the Vitest db project run it against a throwaway PostGIS container before the schema tests.

    

  


  
How they meet

  
The browser draws with #11, validates locally, and sends the closed GeoJSON ring to POST /areas. The route (T15) runs ST_IsValid and ST_Area(geom::geography), inserts into areas and area_versions through the #9 column type, and writes an audit_log row. The client km² you saw above is a preview; the stored area_km2 is the spheroidal value from PostGIS.
