What we are building

A web map where several signed-in people draw areas at the same time and see each other draw live. The map switches between OpenStreetMap and Israel's govmap aerial photos without the drawings moving. Every area gets an accurate size in km², a history of edits, and a conflict check when two people edit at once.

Like you're 5: a shared colouring book on the internet. Everyone colours the same page at the same time, you can swap the paper for a photo from the sky, and the book tells you how big each shape is.

Spec walkthrough (read before D1)

The design spec has nine sections. Each one below is what you are agreeing to, in plain words, with a checkbox so a reviewer can see you read it. Four assumptions I made without asking are pulled out as decisions D11 to D14 after this list.

§2 Architecture

Spec

One deployable unit on Cloudflare: a Worker (Hono) for normal requests, one Room Durable Object per map holding the live WebSocket connections, a RateLimiter Durable Object per user, Postgres/PostGIS on Neon reached through Hyperdrive, a cron job for cleanup, and the React app served as static files by the same Worker. The Worker keeps no state between requests.

Like you're 5: one building. The front desk answers questions, each map has its own playroom where everyone drawing can see each other, and the filing cabinet is in the basement.

§3 Components and boundaries

Spec

Seven parts, each with one job: shared contracts (the Zod schemas both sides use), the Hono app (routes, auth, validation, cache, audit, OpenAPI), the database layer, the auth instance, the Room object, the RateLimiter object, the web app, and the scheduled purge. Rule: coordination state lives only in a Durable Object or in Postgres.

Like you're 5: every helper has one job and a name tag. Nobody keeps secrets in their pocket; everything goes in the shared box.

§4 Data model

Spec

Table areas: id, name (max 120 chars), polygon in WGS84, size in km² computed on the spheroid, a version number, who created it, timestamps, and a soft-delete timestamp. Every change is copied into area_versions. Every mutation writes an audit_log row (user, action, entity, IP, user agent, a hash of the payload). Auth tables come from Better Auth. Polygons are outer ring only (no holes), closed, 3 to 1,000 vertices.

Like you're 5: every shape has a card with its name, its size, and a number that goes up each time someone changes it. We keep every old card too, and a diary of who touched what.

§5 Data flows

Spec

Save: client pre-checks the ring → server validates → rate limit → one transaction (area + version 1 + audit) → room broadcast. Concurrent edit: version check, 409 with the server copy, two-button prompt (D4). Live drawing: vertex deltas at most 10 per second, peers render ghost polygons, newcomers get current drafts on join. Viewport fetch: cache keyed by tile and map version (D6). Layer switch: overlays stored in WGS84, re-added after the swap to the Israel TM projection (D3). Offline: reconnect with backoff, poll every 10 seconds, drafts kept locally.

Like you're 5: when you draw, your friends see your pencil move. When you press save, everyone gets the finished shape. If the internet hiccups, you keep drawing and we catch up.

§6 Error handling

Spec

One error shape everywhere: code, message, optional details. 422 invalid shape (with the PostGIS reason), 401 not signed in, 409 conflict, 429 too many actions with Retry-After, 504 timeout, 500 sanitised. Bad WebSocket frames get an error event and the connection stays open; repeated abuse closes it. Database failures inside the room never crash sockets; clients are told to resync. Structured JSON logs with request id, secrets redacted.

Like you're 5: when something goes wrong you get a short note saying what and why, never a crash, and the grown-ups get a diary entry.

§7 Security

Spec

Sessions in httpOnly secure cookies; the WebSocket upgrade is checked against the same session. CORS with an explicit origin. Zod at every boundary; polygon size caps. Exact per-user rate limiter (D5). Audit log for every mutation and WebSocket draw session. WAF rules on auth routes in production. Health endpoints expose no data. Any signed-in user may edit any area (see D12).

Like you're 5: you need a wristband to come in, you can only draw 50 lines a minute, and the guard writes down who did what.

§8 Testing

Spec

Unit tests for area maths, validation, the rate limiter window, the conflict path, and projection utilities. Worker and Durable Object integration tests on the real workerd runtime with a throwaway PostGIS. An API contract suite run by the Hono CLI. A two-browser Playwright test (D10). Benchmarks: viewport query on 10k polygons, k6 load at 10/50/100 users.

Like you're 5: robots press all the buttons before you do, and two robots draw together to check they can see each other.

§9 Scope boundaries

Spec

In: everything in the brief's sections 1 to 6 plus the bonus items (Docker, tests, OpenAPI, benchmarks). Out, as design notes only: multi-region sharding of rooms, Queues for audit batching, OpenTelemetry export, merging edits beyond rename, restoring a soft-deleted area from the UI.

Like you're 5: we build the whole playground in the drawing, and we write down the three slides we are not building this time.

Assumptions I made without asking

D11 · One shared map, or many maps?

HighTOM-33, 42, 50 · data model

The spec assumes everyone draws on one shared map (one room). The brief says "a map", never "maps". Supporting several maps adds a map entity, a map picker, and a map id on every area and room. It is cheap now and expensive later.

Like you're 5: one big colouring page for everyone, or a book with many pages?

D12 · Who may edit or delete an area

HighTOM-56, 57, 50 · §7

The spec lets any signed-in user edit or delete any area, which matches "collaborative" and makes the conflict feature meaningful. Owner-only editing is safer but turns most of the realtime work into read-only viewing for everyone except the creator.

Like you're 5: can anyone erase anyone's shape, or only the kid who drew it?

D13 · The numbers in the spec

MediumTOM-36, 38, 39, 14

Draft updates at most 10 per second per user. Offline polling every 10 seconds. Presence dropped after 60 seconds of silence. Polygons up to 1,000 vertices. Names up to 120 characters. Viewport results limited per request. These are my defaults; none comes from the brief except the 50 per minute limit.

Like you're 5: how fast your pencil is allowed to move, and how long we wait before we think you went home.

D14 · The out-of-scope list

Medium§9 · README "known limitations"

Design notes only, not code: sharding rooms across regions, Queues for audit batching, OpenTelemetry export, merging concurrent geometry edits beyond rename, and restoring a soft-deleted area from the UI. The brief's "advanced backend optimisation" items are answered as written designs, which matches your earlier scope choice.

Like you're 5: three things we draw on paper but do not build this time.

D3 · What happens if the govmap spike fails

HighTOM-45, 46, 47 · may add a backend ticket

govmap serves aerial tiles on Israel's own grid (EPSG:2039), not the web-standard one, and its licence is unverified. The spike (one day) tries three routes: swap the whole map's projection when you toggle (A), build a server proxy that re-warps tiles (B, about two extra days), or fall back to another imagery provider (C). You decide now which fallback is acceptable so the day ends with a decision, not a question.

Like you're 5: the satellite photos are cut into puzzle pieces of a different shape than our puzzle board. We'll try to make them fit. If we can't, do you want us to build a machine that reshapes them, or use a different photo book?

Licence: if govmap's terms forbid use, C is forced regardless of the technical result.

D4 · How two people editing the same area is resolved

HighTOM-56, 50, 58 · README "technical decisions"

The brief asks for conflict resolution. The plan uses a version number on each area: an update carrying a stale version gets a 409 with the server's copy, and the person is asked to keep theirs, take the other, or just rename. The alternatives are last-writer-wins (simplest, loses work silently) or automatic merging (a CRDT, much more code).

Like you're 5: two kids colour the same drawing at once. We can let the last crayon win, ask them to agree, or try to be a magic crayon that blends both. We suggest asking them.

D2 · Leaflet 1.9.4 or 2.0 alpha

MediumTOM-44, 45, 46, 47, 48

Leaflet 2.0 is modern (ES modules, no global) but still alpha with breaking changes, and the projection plugin we would lean on has not been updated since 2017. 1.9.4 is stable and every example on the web matches it. Either way we write our own projection code on proj4, which ports to 2.0 later.

Like you're 5: there is a shiny new bike with no training wheels yet. The old bike works everywhere. We can ride the old one now and switch later.

D5 · How exact the 50-per-minute limit must be

MediumTOM-29, 40

Cloudflare's built-in rate limiter is fast but approximate (per location, eventually consistent). A tiny Durable Object per user counts exactly. The brief states a precise number, so I lean exact; the binding can still sit in front as a cheap filter.

Like you're 5: you may draw 50 lines a minute. One counter guesses, the other counts every line. The brief gave an exact number, so we count.

D6 · Cache freshness for the map viewport

MediumTOM-59

Viewport queries are cached per map tile. Keeping an index of which tiles each write touches gives instant correctness but more code. A short time-to-live (about 10 seconds) plus a version stamp is far simpler, and realtime events already deliver changes instantly to open clients.

Like you're 5: we keep a photo of the map so we don't redraw it every second. Do we erase the photo the moment anything changes, or just take a new photo every ten seconds?

D7 · One room per map, or sharded by area

MediumTOM-33, 41

A Durable Object is single-threaded with a soft limit of about 1,000 requests per second. One room per map is simplest and ample for this assignment; sharding by map tile is the documented growth path. The choice decides whether sharding is built now or only designed.

Like you're 5: everyone drawing on one map sits in one room with one teacher. If the room gets too full we can split into smaller rooms later. Do we build the extra rooms now or just draw the plan?

D8 · How long deleted areas are kept

MediumTOM-23 · README "retention policy"

Deletes are soft; a scheduled job purges old ones. The number is a policy, not a technical fact. It appears in the README and in the cron.

Like you're 5: when you throw a drawing in the bin, we keep the bin for a while in case you want it back. How long before we empty it?

D9 · Keep the docker-compose Node path

MediumTOM-65, 69

The brief lists docker-compose as a bonus. On Cloudflare the faithful local path is wrangler dev; a Node container means a second WebSocket adapter and an in-process room stand-in, roughly a day. It also makes the reviewer's first run trivial.

Like you're 5: the reviewer wants to press one button and see it run. We can build that button, but it costs a day of extra wiring.

D10 · Two-browser end-to-end test

MediumTOM-64

Unit and integration tests are in scope regardless. A Playwright test that drives two browsers and watches one see the other draw is the strongest proof of the core feature, at about a day.

Like you're 5: we can have a robot open two windows, draw in one, and check the other sees it. It takes a day to teach the robot.
