Plan overview (where we are)

We are in the overview phase: research done, roadmap in Linear, design spec drafted, no code yet. This section is the plan as a human would present it.

What we are building

A web map where several signed-in people draw areas at the same time and see each other draw live. The map switches between OpenStreetMap and Israel's govmap aerial photos without the drawings moving. Every area gets an accurate size in km², a history of edits, and a conflict check when two people edit at once.

Like you're 5: a shared colouring book on the internet. Everyone colours the same page at the same time, you can swap the paper for a photo from the sky, and the book tells you how big each shape is.

D3 · What happens if the govmap spike fails

HighTOM-45, 46, 47 · may add a backend ticket

govmap serves aerial tiles on Israel's own grid (EPSG:2039), not the web-standard one, and its licence is unverified. The spike (one day) tries three routes: swap the whole map's projection when you toggle (A), build a server proxy that re-warps tiles (B, about two extra days), or fall back to another imagery provider (C). You decide now which fallback is acceptable so the day ends with a decision, not a question.

Like you're 5: the satellite photos are cut into puzzle pieces of a different shape than our puzzle board. We'll try to make them fit. If we can't, do you want us to build a machine that reshapes them, or use a different photo book?

Licence: if govmap's terms forbid use, C is forced regardless of the technical result.

D4 · How two people editing the same area is resolved

HighTOM-56, 50, 58 · README "technical decisions"

The brief asks for conflict resolution. The plan uses a version number on each area: an update carrying a stale version gets a 409 with the server's copy, and the person is asked to keep theirs, take the other, or just rename. The alternatives are last-writer-wins (simplest, loses work silently) or automatic merging (a CRDT, much more code).

Like you're 5: two kids colour the same drawing at once. We can let the last crayon win, ask them to agree, or try to be a magic crayon that blends both. We suggest asking them.

D2 · Leaflet 1.9.4 or 2.0 alpha

MediumTOM-44, 45, 46, 47, 48

Leaflet 2.0 is modern (ES modules, no global) but still alpha with breaking changes, and the projection plugin we would lean on has not been updated since 2017. 1.9.4 is stable and every example on the web matches it. Either way we write our own projection code on proj4, which ports to 2.0 later.

Like you're 5: there is a shiny new bike with no training wheels yet. The old bike works everywhere. We can ride the old one now and switch later.

D5 · How exact the 50-per-minute limit must be

MediumTOM-29, 40

Cloudflare's built-in rate limiter is fast but approximate (per location, eventually consistent). A tiny Durable Object per user counts exactly. The brief states a precise number, so I lean exact; the binding can still sit in front as a cheap filter.

Like you're 5: you may draw 50 lines a minute. One counter guesses, the other counts every line. The brief gave an exact number, so we count.

D6 · Cache freshness for the map viewport

MediumTOM-59

Viewport queries are cached per map tile. Keeping an index of which tiles each write touches gives instant correctness but more code. A short time-to-live (about 10 seconds) plus a version stamp is far simpler, and realtime events already deliver changes instantly to open clients.

Like you're 5: we keep a photo of the map so we don't redraw it every second. Do we erase the photo the moment anything changes, or just take a new photo every ten seconds?

D7 · One room per map, or sharded by area

MediumTOM-33, 41

A Durable Object is single-threaded with a soft limit of about 1,000 requests per second. One room per map is simplest and ample for the product brief; sharding by map tile is the documented growth path. The choice decides whether sharding is built now or only designed.

Like you're 5: everyone drawing on one map sits in one room with one teacher. If the room gets too full we can split into smaller rooms later. Do we build the extra rooms now or just draw the plan?

D8 · How long deleted areas are kept

MediumTOM-23 · README "retention policy"

Deletes are soft; a scheduled job purges old ones. The number is a policy, not a technical fact. It appears in the README and in the cron.

Like you're 5: when you throw a drawing in the bin, we keep the bin for a while in case you want it back. How long before we empty it?

D9 · Keep the docker-compose Node path

MediumTOM-65, 69

The brief lists docker-compose as a bonus. On Cloudflare the faithful local path is wrangler dev; a Node container means a second WebSocket adapter and an in-process room stand-in, roughly a day. It also makes the reviewer's first run trivial.

Like you're 5: the reviewer wants to press one button and see it run. We can build that button, but it costs a day of extra wiring.

D10 · Two-browser end-to-end test

MediumTOM-64

Unit and integration tests are in scope regardless. A Playwright test that drives two browsers and watches one see the other draw is the strongest proof of the core feature, at about a day.

Like you're 5: we can have a robot open two windows, draw in one, and check the other sees it. It takes a day to teach the robot.
