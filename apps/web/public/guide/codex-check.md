## Disagreements with the matrix

Compared with `criteria-matrix.md` (served next to this file):

1. **The 50-action requirement is not an unqualified "Met".** The number and rolling-minute window are exact, but the unit is draft sessions plus REST changes. The test expressly permits more than 50 drawing edits inside one session. The matrix acknowledges this later but still marks the requirement Met.
2. **Smooth transition is only partly established.** A tested animation call proves a fade exists. It does not prove the new imagery is ready when the old snapshot disappears, or that switching stays visually smooth on slow tile loads.
3. **High-volume WebSocket message queuing is not delivered as worded.** Ordering buffers are present, but direct socket fan-out is the delivered behaviour. The matrix's Partial gives those buffers credit for a different purpose.
4. **Compose is no longer database-only.** Current `main` contains an optional API/workerd container. The matrix's Docker row and limitation saying the container was never built are outdated. Whole-product containerization remains partial because Vite stays on the host.
5. **OpenAPI coverage is partial across the exposed API.** The reference exists and documents the area/health operations, but omits authentication and the WebSocket exchange. The matrix discloses those omissions while assigning an unqualified Met.
6. **The broad positive rows should carry their underlying gaps.** I assess the overview's real-time workflow, core realtime focus, backend scalability focus, database optimization focus, real-time implementation evaluation, database-performance evaluation and map-transition evaluation as partial overall. The matrix marks these Met despite limitations in their constituent features.
7. **Documentation is substantial but not fully consistent.** ADR-0004 still describes draft frames as spending the shared budget; the README, protocol tests and actual delivered behaviour count sessions. That prevents an unqualified positive documentation assessment.
8. **The claim that REST writes "never wait on the Room" is incorrect.** They wait for a bounded map-version bump before responding; broadcast delivery happens afterward. Failure is tolerated, but the wait exists.
9. **Backend code organization is not a feature verdict.** I do not adopt the matrix's quality judgment; this check confirms the documented architecture and delivered behaviour only.
10. **Saved CI/production evidence does not verify this checkout.** The matrix audits `1a581e7`; this checkout is `267deb2`. The saved CI successes and readiness observation concern earlier commits. Current GitHub source completeness, CI success and deployed behaviour remain unverified.

I agree with the matrix's substantive findings on incomplete viewport retrieval, insufficient dense-region evidence, incomplete action auditing, legacy govmap dependency, zoom changes, and limited load-test scale. Cookie session tokens do satisfy authenticated WebSockets; the wording does not require a separate bearer token.

## Missed by the matrix

- **Cancelling and redrawing does not necessarily start a new budgeted session.** Clear followed by new vertices remains in the existing session until save or idle expiry. The draft-session test checks this explicitly.
- **Visible edit history is limited independently of retained history.** Only the newest 200 versions are returned; the screen exposes no pagination. Deleted areas return 404 for history even before their retained records are purged.
- **Bounds results can include areas outside the actual viewport.** The API expands bounds to a grid and compares polygon bounding boxes. This is separate from the missing-results problem caused by the cap.
- **The live area display changes units.** Areas below 1 km² display whole m²; larger areas display km² to three decimals. The API consistently returns km².
- **Presence means connected, reported state.** It does not establish that someone is actively looking at the browser. "Drawing" is triggered by drawing changes, so merely pressing the draw button does not immediately report it.
- **The fade does not wait for loaded replacement tiles.** The old snapshot is removed after the animation finishes. This is the specific unverified part of "smooth transition".
- **A failed invalidation can produce stale reads even after a successful save.** If the version bump fails and fan-out does not repair it, an available old cache entry can remain usable for its 30-second lifetime. This is distinct from the already-listed overlapping-read race.
- **Metric collection has loss and interpretation limits.** Deploy/crash eviction can lose one pending message-count window; socket closes are not always recorded, so opens minus closes is not an active-user count.
- **The container's operational limits now matter.** The API profile is opt-in, requires the host secrets file, and loses its Durable Object state when recreated; the database volume persists.
- **The saved production metrics are small observations.** Database-write latency is based on two points and read latency on 31 points. They demonstrate collection, not production load capacity.
- **Some documentation overstates its own coverage.** Cache comments describe holding "every area" despite the 500 cap, and deploy documentation refers to audit-log retention without a corresponding purge policy in the retention behaviour inspected.

All these findings come from the README, API descriptions, screens, protocol, compose configuration, recorded evidence, or test assertions Codex read; no live browser, fresh CI run, deployment or load test was performed. I only forwarded the Codex run and did not check its claims myself. The one edit I made to its output: the matrix link is now a plain absolute path, and the "Where" column for the first rows is as Codex gave it.
